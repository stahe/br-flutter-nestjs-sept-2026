    Este documento é a continuação do curso “Um exemplo cliente/servidor - AngularJS 1.x / Spring 4,” escrito em 2014. Esse documento original construía uma pequena aplicação de agendamento de consultas médicas (“[RdvMedecins]”) usando um servidor Spring 4 / Spring Data / Spring MVC e um cliente AngularJS 1.x.

    Doze anos depois, os dois frameworks utilizados evoluíram bastante, ou até foram substituídos no uso corrente:

    • no lado do servidor, o [NestJS] se firmou como um dos frameworks Node.js/TypeScript mais usados para construir aplicações web estruturadas, com uma filosofia semelhante à do Spring (módulos, controllers, serviços, injeção de dependência), mas dentro do ecossistema JavaScript/TypeScript;
    • no lado do cliente, o AngularJS 1.x foi completamente reescrito a partir de 2016 com o nome [Angular] (versões 2, 4, 5… até a versão 22) - a abordagem adotada pela variante [Angular] / [NestJS] deste curso: Um exemplo cliente/servidor - Angular / NestJS (2026). Este documento adota uma abordagem diferente: [Flutter] (criado pelo Google, primeira versão estável em dezembro de 2018), um framework “multiplataforma” que, a partir de uma única base de código escrita na linguagem [Dart], gera aplicações mobile, desktop e web, cuja interface é descrita não por templates HTML, mas por uma árvore de widgets (veja o Capítulo 3).

    O objetivo deste documento é revisitar o estudo de caso original (a mesma aplicação, as mesmas funcionalidades, o mesmo banco de dados) e reconstruí-lo com as ferramentas atuais, mantendo o máximo possível a mesma progressão didática do documento de 2014.

    1.1. Uma reconstrução passo a passo

    O documento original tinha cerca de 300 páginas e cobria, além das funcionalidades centrais da aplicação (autenticação baseada em papéis, com Spring Security), doze exemplos progressivos para aprender AngularJS 1.x passo a passo. Reconstruir todo esse conteúdo de uma só vez seria demorado e difícil de assimilar.

    Este documento cobre, portanto, as duas primeiras etapas da reconstrução:

    • a arquitetura geral da aplicação (inalterada em princípio);
    • o banco de dados (inalterado, exceto pela adição da tabela [users]);
    • a instalação do servidor [NestJS] completo fornecido com este documento, cujas funcionalidades de consulta e de marcação/cancelamento de consultas são testadas com o Postman (seu código não é abordado aqui, pois este documento é dedicado ao [Flutter]);
    • a autenticação por token (JWT) e o controle de acesso por papéis (ADMIN/USER) para esse servidor, equivalente à camada Spring Security do documento original (aprenderemos apenas a usá-lo, primeiro por meio do Postman e depois pelo cliente);
    • o cliente [Flutter] correspondente, com as mesmas funcionalidades: uma tela de login, uma interface adaptada ao papel do usuário conectado ([Material Design]) e a possibilidade de alternar a interface entre francês e inglês ([TranslationsService]).

    Duas funcionalidades do documento original ficam, nesta etapa, fora deste documento: o modo “debug” do cliente original (exibição do template bruto da view atual), que foi deliberadamente omitido desta portabilidade (veja o Capítulo 6 para a justificativa dessa decisão), e a configuração de um atraso de rede artificial, que foi adiada para uma etapa posterior.

    1.2. A quem se destina este documento

    Este documento não pressupõe nenhum conhecimento prévio de [NestJS] nem de [Flutter]. Cada novo conceito (decorador, injeção de dependência, componente, signal etc.) é explicado quando aparece, com o maior detalhe possível, mesmo para leitores que nunca escreveram uma única linha de TypeScript ou Dart.

    No entanto, alguns conhecimentos básicos ajudam a aproveitar melhor este documento:

    • noções básicas da linguagem Dart (variáveis, funções, arrays, objetos);
    • noções básicas das interações HTTP em uma aplicação web (métodos GET/POST, formato JSON);
    • as tags mais comuns da linguagem HTML;
    • o uso da linha de comando (cd, npm install…).

    Não é preciso conhecer previamente a linguagem TypeScript (usada no lado do servidor): ela é um superconjunto do JavaScript que acrescenta um sistema de tipos, explicado ao longo do documento sempre que for usado. O mesmo vale para a linguagem [Dart], usada no lado do cliente, que é apresentada no Capítulo 3. Os leitores interessados podem consultar o documento *Introdução à linguagem Dart por meio de exemplos* (2026), que explica o Dart em detalhes.

    1.3. A arquitetura da aplicação

    A arquitetura geral da aplicação não mudou desde o documento original:

    • um servidor web fornece ao cliente uma interface única, construída sobre o modelo de Componentes (view + lógica associada), que se apoia em serviços para se comunicar com o servidor: um navegador para os clientes [Angular]/[React]/[Vue.js] deste curso ou, para este cliente [Flutter], um navegador, um sistema operacional mobile ou um sistema operacional desktop (veja o Capítulo 5);
    • o usuário interage com as views exibidas no navegador. Suas ações às vezes exigem uma requisição ao servidor [NestJS], que processa a requisição e devolve uma resposta JSON (JavaScript Object Notation); essa resposta é usada para atualizar a view apresentada ao usuário.

    A aplicação em questão terá a seguinte arquitetura:

    • Em [1], o usuário da aplicação [Flutter] consulta a camada [Presentation] [2] dessa aplicação;
    • para realizar a ação solicitada pelo usuário, a camada [Presentation] [2] pode consultar a camada [Services] [3];
    • para fornecer o serviço solicitado, a camada [3] pode precisar consultar [4], o servidor JSON remoto implementado pelo [NestJS];
    • Dependendo da requisição recebida em [5], as camadas [6-8] podem ser consultadas;
    • a resposta do servidor percorre as camadas [2-8] em ordem inversa;
    • a view exibida ao usuário, [1], reflete essa resposta;

    Nota: Se a arquitetura do projeto parecer confusa, volte a este diagrama. Observe que o SGBD é usado pelo servidor, não pelo cliente.

    1.4. Ferramentas utilizadas

    Este documento usa as seguintes ferramentas (sua instalação é detalhada nos Capítulos 1 e 2):

    • Node.js (versão 22 ou posterior) e seu gerenciador de pacotes npm, o equivalente, no ecossistema JavaScript, do que Java + Maven eram para o servidor Spring original;
    • Visual Studio Code (VSCode), um editor de código gratuito, com suas extensões para TypeScript, o equivalente do Spring Tool Suite (STS) e do WebStorm usados no documento original;
    • o SDK do [Flutter] (que inclui o SDK do [Dart]) é instalado uma única vez, em todo o sistema, ao contrário do [Vite], usado pelos clientes web anteriores deste curso, que não exigia nenhuma instalação em todo o sistema;
    • [MySQL] 8 para o banco de dados (o documento original usava o [MySQL] 5; o esquema relacional em si não muda);
    • [Android Studio] (com seu SDK do [Android] e suas ferramentas de linha de comando), para compilar a aplicação em um celular [Android], o destino mobile deste curso; as instruções detalhadas de instalação estão no Capítulo 1;
    • Postman (ou qualquer outro cliente HTTP), para testar as URLs do servidor que respondem a requisições POST (/addAppointment, /deleteAppointment); um navegador web só consegue testar requisições GET.

    1.5. Funcionalidades da aplicação

    As funcionalidades de “negócio” da aplicação [RdvMedecins] permanecem inalteradas em relação ao documento original; o controle de acesso, porém, é um pouco mais robusto que o original (veja a tabela abaixo):

    • Um consultório médico emprega vários médicos, cada um com seus próprios horários de atendimento;
    • um usuário deve fazer login (nome de usuário/senha) para acessar a aplicação;
    • Uma vez conectado, o usuário pode selecionar um médico e um dia e ver a agenda do médico nesse dia: cada horário aparece como disponível ou reservado;
    • um usuário com o papel ADMIN também pode reservar um horário disponível para um paciente de sua escolha e cancelar uma consulta existente;
    • Um usuário com o papel USER pode ver as agendas, mas não pode marcar nem cancelar consultas (acesso somente leitura), uma diferença deliberada em relação ao documento original, no qual o papel USER servia apenas para ilustrar uma negação de acesso e não podia ver absolutamente nada (veja o Capítulo 2, seção “Criação do banco de dados”, para a justificativa dessa escolha).

    1.7. Organização deste documento

    1. Configuração do ambiente de trabalho: instalar as ferramentas e criar o projeto [Flutter].
    1. Instalação do servidor [NestJS]: instalar o Laragon e o banco de dados [MySQL], configurar, iniciar e testar o servidor e, em seguida, executar o cliente [Flutter] pela primeira vez.
    2. Introdução ao [Flutter]: as bases do framework (widgets, StatelessWidget/StatefulWidget, provider), com uma revisão de conceitos já vistos em [Angular], [React] e [Vue.js].
    3. O cliente [Flutter] da aplicação [RdvMedecins]: a arquitetura do cliente, cada um de seus arquivos (incluindo a tela de login) e um passo a passo de toda a aplicação.
    4. Portabilidade da aplicação [Flutter] para mobile, desktop e web: como um único código-fonte é compilado para essas três famílias de destinos e o que é preciso saber sobre cada uma delas (rede, restrições específicas do mobile).
